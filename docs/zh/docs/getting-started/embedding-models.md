# 嵌入模型

嵌入模型（Embedding Models）将文本转换为捕捉语义含义的数值向量，从而实现语义搜索、文档相似度和智能上下文检索等强大功能。

## 什么是嵌入模型？

与生成文本响应的聊天模型不同，嵌入模型产生固定长度的数值数组（向量），用于表示文本的含义。这些向量可用于：

- **语义搜索**：按含义而非关键词查找内容
- **文档相似度**：比较两段文本的相关程度
- **上下文检索**：为 AI 对话查找相关信息
- **记忆增强**：通过查找相关的过去对话来改善助手记忆

## Kelivo 如何使用嵌入

Kelivo 在模型选择界面中自动将嵌入模型与聊天模型分开归类。这有助于您：

1. **识别模型类型**：嵌入模型分组在专门的"嵌入"类别下
2. **正确选择**：为特定功能选择嵌入模型
3. **避免混淆**：嵌入模型不能用于常规聊天

### 模型类型检测

Kelivo 通过以下方式识别嵌入模型：
- 来自供应商的模型类型元数据
- 模型 ID 包含 "embedding" 或 "embed"

查看可用模型时，请查找 **嵌入** 分组来找到这些专用模型。

## 支持的嵌入模型

### OpenAI

| 模型 | 维度 | 用途 |
|------|------|------|
| `text-embedding-3-small` | 1536 | 性价比高，质量好 |
| `text-embedding-3-large` | 3072 | 最高质量 |
| `text-embedding-ada-002` | 1536 | 旧版，仍然支持 |

**配置**：
- 基础地址：`https://api.openai.com/v1`
- 端点：`/embeddings`

### Google (Gemini)

| 模型 | 维度 | 用途 |
|------|------|------|
| `text-embedding-004` | 768 | 通用 |
| `embedding-001` | 768 | 旧版模型 |

**配置**：
- 使用 Google AI Studio 或 Vertex AI
- 通过 Gemini API 提供

### Anthropic

Anthropic 目前不提供独立的嵌入模型。如需与 Claude 配合使用嵌入功能，可以考虑：
- 使用 OpenAI 或 Google 嵌入模型
- 第三方嵌入服务

### 自定义/自托管

许多供应商通过 OpenAI 兼容 API 提供嵌入模型：

| 供应商 | 常用模型 |
|--------|----------|
| Ollama | `nomic-embed-text`, `mxbai-embed-large` |
| Hugging Face | `sentence-transformers/*` |
| Cohere | `embed-english-v3.0`, `embed-multilingual-v3.0` |
| Jina AI | `jina-embeddings-v2-base-en` |
| Voyage AI | `voyage-large-2`, `voyage-code-2` |

## 设置嵌入模型

### 步骤 1：添加支持嵌入的供应商

1. **打开设置** → **服务供应商**
2. **添加或选择** 提供嵌入模型的供应商
3. **确保 API Key 有权** 访问嵌入端点

### 步骤 2：获取可用模型

1. **打开供应商设置**
2. **点击"获取模型"** 或"刷新模型"
3. **查看嵌入分类** 在模型列表中
4. **验证嵌入模型** 是否出现

### 步骤 3：配置功能

嵌入模型被某些 Kelivo 功能自动使用：
- **记忆**：用于检索相关上下文
- **文档搜索**：当为助手启用时
- **语义匹配**：用于查找相似对话

## 模型选择建议

### 通用用途

**推荐**：`text-embedding-3-small`（OpenAI）
- 质量和成本的良好平衡
- 广泛兼容
- 处理速度快

### 高精度需求

**推荐**：`text-embedding-3-large`（OpenAI）
- 最佳质量嵌入
- 每次调用成本较高
- 更大的向量维度

### 节省成本

**推荐**：Google 嵌入模型或自托管选项
- 通常每 token 成本更低
- 大多数用例质量良好
- 可能有使用限制

### 专业任务

| 任务 | 推荐模型 |
|------|----------|
| 代码搜索 | `voyage-code-2` |
| 多语言 | `embed-multilingual-v3.0`（Cohere） |
| 本地/私有 | `nomic-embed-text`（Ollama） |
| 长文档 | 支持 8K+ 上下文的模型 |

## 理解嵌入维度

嵌入维度影响：

| 高维度 | 低维度 |
|--------|--------|
| 捕捉更多语义细节 | 处理更快 |
| 准确度更高 | 内存使用更少 |
| 需要更多存储 | 更具性价比 |
| 相似度计算更慢 | 可能丢失细微含义 |

**典型范围**：
- 小型：384-768 维
- 中型：1024-1536 维
- 大型：2048-3072+ 维

## 最佳实践

### 1. 保持一致性

对相关操作使用 **相同的嵌入模型**：
- 如果用 `text-embedding-3-small` 嵌入文档，搜索时也使用同一模型
- 切换模型会使现有嵌入失效

### 2. 文本分块

对于长文档：
- 分割成有意义的块（段落、章节）
- 典型块大小：256-512 个 token
- 块之间包含重叠以保持上下文

### 3. 预处理

提高嵌入质量：
- 移除不必要的空白
- 规范化格式
- 考虑为搜索移除停用词

### 4. 缓存

嵌入是确定性的：
- 为静态内容缓存嵌入
- 仅在内容变化时重新嵌入
- 节省 API 成本和处理时间

## 成本考虑

嵌入模型通常比聊天模型更便宜：

| 供应商 | 模型 | 大约成本 |
|--------|------|----------|
| OpenAI | text-embedding-3-small | $0.02/百万 token |
| OpenAI | text-embedding-3-large | $0.13/百万 token |
| Google | text-embedding-004 | 通常有免费额度 |
| 自托管 | Ollama 模型 | 免费（仅计算成本） |

**成本优化建议**：
- 批量嵌入多个文本
- 缓存常用嵌入
- 在质量允许时使用较小的模型
- 大量使用时考虑自托管

## 故障排除

### 找不到嵌入模型

1. **检查供应商配置**：确保 API Key 有嵌入访问权限
2. **刷新模型列表**：在供应商设置中点击"获取模型"
3. **验证模型可用性**：某些供应商需要单独的访问权限

### 搜索结果不佳

1. **验证使用相同模型**：嵌入和搜索必须使用同一模型
2. **检查文本预处理**：格式不一致会影响结果
3. **调整块大小**：块太大或太小都会降低准确度

### 延迟高

1. **使用较小维度**：低维度模型更快
2. **批量请求**：一次发送多个文本
3. **考虑本地模型**：Ollama 消除网络延迟

### 内存/存储问题

1. **减少维度**：使用较小的嵌入模型
2. **限制历史**：不要无限期嵌入所有内容
3. **清理旧嵌入**：删除过期的嵌入内容

3. 根据对话上下文检索相关记忆
4. 检索到的记忆包含在提示词中
